# My Whiteboard 0.2 Implementation Brief

## Product boundary

My Whiteboard is an Agent-neutral, local-first shared visual workspace. It is not an Agent runtime, model gateway, chat client, desktop automation layer, or autonomous coordinator.

## Target architecture

```text
Codex Plugin      Claude Code      Other MCP Client
      \                |                /
                 MCP Adapter
                      |
             My Whiteboard Core
       Project / Entities / Transactions
          |          |           |
     Local Store  Event Log   Cloud Adapter
          |
     Semantic Board State
          |
     Excalidraw Adapter
          |
  Standalone Web Workspace
```

Core contains no client-specific branches. Codex packaging and Claude configuration are adapters around the same stdio MCP entry point.

## Project model

```text
Project
├── Overview
├── Shared Context
├── Tasks
├── Boards
│   └── Semantic Elements + Layout
├── Decisions
├── Artifacts
├── Agents
├── Handoffs
├── Messages
├── Selection Context
└── Event Log
```

Every mutable entity has its own `version`. The Project Workspace has a monotonically increasing `workspaceVersion`.

## Version semantics

- `workspaceVersion` increments once per committed transaction and orders the Event Log.
- Entity `version` increments only when that entity changes.
- Mutations include the expected version of each updated or deleted entity.
- Unrelated entity updates can commit even when the caller's observed workspace version is older.
- A stale version of the same entity returns a structured conflict and does not write.
- Delta Context is produced by filtering events after a caller-supplied workspace version.

## Persistence

New project data lives at:

```text
<project>/.my-whiteboard/
├── workspace.json
├── snapshots/
├── imports/
└── lock
```

For the first correct implementation, `workspace.json` atomically contains current entities and the authoritative event log. Mutations acquire a cross-process lock, reload state, validate expected entity versions, append events, then atomically replace the file. Snapshots are recovery artifacts, not an alternate authority.

Event-log compaction is explicitly deferred until real workloads justify it.

## Semantic Board State

The canonical board stores semantic elements and presentation separately inside one state:

```text
Semantic Element
├── id / kind / semanticType / label
├── properties / relations / code references
├── status / owner / related task / risks / tests
├── version
└── layout
```

Initial kinds: `node`, `edge`, `text`, `note`, `group`, and `section`.

Agents may omit layout. A deterministic layout service supplies defaults. Excalidraw scenes are projections generated by the adapter. User edits are converted into semantic create/update/delete mutations before persistence; raw Excalidraw scene JSON is never stored as a second canonical document.

## Excalidraw integration

- Use the official `@excalidraw/excalidraw` React package through a bundled standalone workspace.
- Project semantic state is converted to Excalidraw initial elements.
- Excalidraw `onChange` is diffed against the last projection and translated into semantic transactions.
- Stable semantic IDs are carried in Excalidraw element metadata.
- Unsupported Excalidraw-only features remain session-only until the Semantic Board schema explicitly supports them.
- Legacy SVG is retained only for import comparison, migration verification, and emergency rollback.

## Compatibility plan

1. Discover legacy `<project>/.codex/whiteboards/*.whiteboard.json` files.
2. Copy each source file into `.my-whiteboard/imports` before conversion.
3. Convert legacy shapes, connectors, grouping, styles, and code metadata into Semantic Board elements.
4. Record source hash, migration time, target board ID, and warnings.
5. Never delete or rewrite the legacy source.
6. Re-running the importer with the same source hash is idempotent.

## MCP direction

New tools are workspace-oriented and batch-first:

- Project discovery/create/open.
- Workspace snapshot and delta reads.
- Semantic `board.apply` transactions.
- Shared context, task, decision, artifact, agent, handoff, and message batches.
- Persisted selection context reads.
- Standalone workspace URL opening.

Legacy board tools remain compatibility wrappers during the migration window and use Semantic Board State after import.

## Milestones

### M1 — Single-Agent Board Integration

- Project create/open.
- Semantic Board create/read/apply.
- Excalidraw standalone workspace.
- User edits persist as semantic mutations.
- Code references, selection, export, migration, history, and re-read by Codex.

### M2 — Single-Agent Workspace

- Shared Context.
- Tasks and dependencies.
- Decisions.
- Artifacts.
- Agent Identity.
- Workspace delta reads.
- Full real Codex acceptance flow.

### M3 — Multi-Agent Workspace

- Second Agent join and status.
- Assignment and Handoff.
- Project Messages.
- Entity conflict detection.
- Codex to Claude to Codex closed-loop test without copied private chat.

## Test strategy

- Unit tests for schema normalization, transactions, lock behavior, versions, and deltas.
- Migration fixtures for every legacy element type and code metadata.
- Adapter round-trip tests that assert Semantic State remains authoritative.
- MCP integration tests against the stdio server.
- Browser tests for user edit persistence and selection.
- Concurrent-process conflict tests.
- Real Codex and Claude Code acceptance tests reported separately from mocks.
